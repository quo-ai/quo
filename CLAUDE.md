# Quo

Privacy-first on-device AI assistant. Every version lives in this repo; each app is its own npm project (run commands inside its folder):

- **`apps/mobile/`** — phone apps (Expo / React Native). Details below; paths in that section are relative to `apps/mobile/`.
- **`apps/web/`** — Quo Web (Vite + React, wllama in the browser) and its API (`server/`, plain Web Request → Response; relative imports carry `.js` extensions so they run as native ES modules). `npm run dev`, `npm run typecheck`, `npm test`; hosting, environment variables and self-hosting in apps/web/README.md; end-to-end encrypted sync in apps/web/SYNC.md. Live at app.quo.computer on Quo's own Windows server (Apache behind Cloudflare, `QuoWeb` service, Neon Postgres) via `bash ops/deploy-server.sh`. **`ops/` holds Quo's own hosting and deploy scripts and notes (ops/README.md); it is gitignored and never committed** — keep anything specific to Quo's own machines, accounts or hosting there, out of the repo. Cloudflare closes a silent request at 100 s: keep streams talking and requests under 90 s. Deploys reload the app without dropping requests (`server/reload.ts`; a reload also takes changed settings): never restart the QuoWeb service to deploy or to change a setting. What the cloud costs is kept as daily totals with nothing about who (`server/costs.ts`); `bash ops/stats-server.sh` prints them with sales, Pro allowance use and conversion. The old address, `quoai-app.vercel.app`, still runs the full app on Vercel (same database) because desktop 1.5.0 and the Android app have it built in: keep it deployed (`bash ops/deploy-vercel-app.sh`) until updates with the new address are out.
- **`apps/desktop/`** — Electron app that serves a Quo Web build (`../web/dist`) from `app://quo` and runs models in a native llama.cpp `llama-server` process (pinned in `engine.lock.json`); see apps/desktop/README.md (`npm run fetch:engine`, `npm run dev`, `npm test`, `npm run smoke`). Releases come from `desktop-v*` tags; Windows builds are unsigned (SignPath Foundation declined until Quo is better known; a certificate needs only the `WIN_CSC_LINK` secrets) and the Mac app stays ad-hoc signed (apps/desktop/README.md → Signing).
- **`website/`** — static site (quo.computer, served by Quo's own server; quoai.vercel.app forwards to it). Document pages (privacy, terms, refunds, pricing, support, brand, delete account, 404), the sitemap and llms.txt are generated by `website/scripts/generate-pages.py` from index.html's header and footer; edit the script, not the pages. The script also writes each page's Markdown copy (`index.md`), the pages' structured data (`structured_data.py`: only words the page shows), the home page's questions data (between the `questions-data` marks in index.html) and the sitemap's dates (from git, never by hand). It uses the apps' look: `website/assets/tokens.css` is written by `npm run tokens` in apps/web (tested), and the fonts are the apps' own. Product pictures in `assets/shots/` show light and dark versions to match the visitor. Deploy with `bash ops/deploy-website.sh`.

## Phone apps

Privacy-first on-device AI chat app. Expo SDK 57 / React Native 0.86 (New Architecture), llama.rn for local GGUF inference, single lifetime IAP (`quopremium`). Android ships a bundled starter model via Play Asset Delivery.

### Commands

- `npm run typecheck` — tsc, strict mode; must stay clean
- `npm test` — jest (jest-expo preset); pure-logic tests, native modules mocked in jest.setup.js
- `npm run lint` — 0 errors required; ~90 react-hooks v6 warnings are a known gradual burn-down (see eslint.config.js)
- `npm run android` / `npm run ios` — local dev build (Android emulators need an arm64 image; x86 is not built)
- `npm run sandbox [-- build|start|logs|shell|down|clean]` — Linux: Android dev loop in a rootless podman container (scripts/android-sandbox.sh, scripts/sandbox/Containerfile) on a USB phone; repo mounted read-only, writable state in podman volumes. Fedora needs `container_use_devices` SELinux boolean on. Use `build` after native/dependency changes; JS changes hot-reload
- `npm run ios:release` / `ios:release:upload` — App Store archive/upload (macOS only; see docs/ios-release.md in apps/mobile)
- `npm run fetch:starter-model` — downloads the ~530MB starter GGUF into the Android asset pack (release builds; runs automatically on EAS via `eas-build-post-install`)

### Architecture

- `app/` — expo-router. Root layout gates: AppLoading → ModelSelectionScreen (onboarding, outside the router) → `(drawer)` group (Chat `index`, Settings).
- `contexts/ChatContext.tsx` — central store: conversations, model lifecycle, streaming, tool loop, context compression, persistence. `contexts/PremiumContext.tsx` — entitlement/paywall.
- `services/` — singleton modules (`llmService`, `downloadService`, …) with manual listener-set pub/sub. Pure llm logic lives in `services/llm/` (prompt, tokens, compression, params); shared resumable-download helper in `services/fileDownload.ts`.
- `components/settings/`, `components/message/`, `components/onboarding/` — section/piece components for the three big screens.
- `constants/premium.ts` — single source of truth for PREMIUM_FEATURES, FREE_TIER_LIMITS, price fallback (PremiumContext re-exports for UI imports). `constants/models.ts` — model catalog incl. per-model settings, mmproj, draft models.
- Styling: plain StyleSheet + tokens from `constants/theme.ts` (light and dark palettes that follow the device setting). No tailwind/nativewind.

### Critical gotchas

- **Hexagon DSP is disabled in four places** (crashes on non-Qualcomm devices). The list is in `plugins/withLlamaFix.js`'s header comment — revisit all four on any llama.rn bump.
- `scripts/apply-native-patches.js` (postinstall) is the single source of truth for node_modules patches; it throws loudly when a dependency bump invalidates a patch — fix the patch, don't delete it.
- Model files must stay uncompressed for mmap: `noCompress += ['gguf']` in app/build.gradle. The Android starter model is a **fast-follow** Play Asset Delivery pack (`android/starter_model_pack`): Play downloads it right after install and it's loaded in place from the pack's file path via the local Expo module `modules/asset-packs` (no copy). First launch follows the pack's progress (`deliverStarterPack` in `services/bundledModel.ts`); installs without the pack (sideloaded/dev) fall back to the HF download. Test the real flow with `npm run sandbox -- bundle` (bundletool local testing); verify app *updates* on the Play internal track — local testing can't.
- Downloads are validated by size (95% of expected). Never accept a download on `result.uri` alone — truncated GGUFs pass existence checks and crash at initLlama. `isModelFileValid` (services/llm/paths.ts) is the one validity rule (≥95% of catalog `sizeBytes` + GGUF magic); catalog `sizeBytes` must be exact byte counts. Downloads/copies go to `.tmp`/`.part` and are moved into place only after validating.
- Storage is one AsyncStorage row per conversation + an index key (Android CursorWindow ~2MB limit). Don't reintroduce a single-blob write. `saveConversations` never deletes rows — removal is explicit via `deleteConversationRows`/`clearConversationRows`. Recall vectors live in files under `documentDirectory/recall/`, not AsyncStorage.
- llama.rn ignores the token callback's return value: native work only stops via `stopCompletion()`. `llmService.generate()` serializes completions (a new one aborts and awaits the previous) and streams the **full** visible text each update, not deltas; never `release()` a context while `isCompleting`.
- Streaming text lives in `StreamingContext` (`useStreaming()` → `{content, conversationId}`), not in `useChat()` — keep it out of the main context so token updates don't re-render the app. ChatContext init waits for PremiumContext to finish loading (running as "free" first used to delete premium users' chats).
- Model selection is persisted only after a successful load; a pending-load marker detects OOM-kills during load and falls back to the starter on next launch (contexts/chat/useModelLifecycle.ts).
- Do not run `expo prebuild` casually for **Android** — `android/` contains hand-maintained customizations (asset pack, signing helper, gradle heap/task tweaks). **iOS is the opposite**: `ios/` is not committed (gitignored); it's generated by `npx expo prebuild -p ios` (`npm run ios` and `npm run ios:release` do this). All iOS config — usage strings, entitlements, Firebase file, static frameworks — lives in app.json and the config plugins; never hand-edit the generated project.
- iOS Firebase needs the real `GoogleService-Info.plist` at repo root (gitignored; see the committed .example). Without it, iOS analytics/crashlytics/remote-config silently no-op.
- **Quo Sync on the phone** (`services/sync/`, UI in `components/settings/SyncSection.tsx` and the `components/settings/sync/` folder). Chats are read and written *through the chat context* (`services/sync/bridge.ts`, `contexts/chat/syncBridge.ts`), never straight to AsyncStorage: `conversationsRef` in ChatContext is the synchronous source of truth and `setConversations` is a wrapper that updates it first, so a sync write can't land on top of an edit made in the same moment (it checks the chat's fingerprint and retries). Sync deletions and the free tier's trimming are `quiet` (`deleteConversationRows(ids, { quiet: true })`), so they're never announced back as user deletions, and `markSyncApplied` stops what sync wrote being re-uploaded as an edit. The key and sign-in token live in `expo-secure-store`; both it and `expo-crypto` are native modules, so the first release with Sync needs a new native build, not an OTA update. There are deliberately no purchase flows for Sync in the app (Play Billing policy); it only tells people the plan comes with their Quo account.
- Both platforms bundle the starter model (Android: fast-follow Play Asset Delivery pack; iOS: app-bundle resource via plugins/withIosBundledModel — canonical file in gitignored assets-native/bundled-models/, fetched by scripts/fetch-starter-model.js). Deliberate gap: iOS pauses generation when backgrounded (Android keeps going behind an ongoing notification).

## Web and desktop gotchas

- **Services that aren't set up answer `503 setup_required`, they are not hidden.** Sign-in, paid models, purchases and Quo Sync stay visible in the app and show a plain "not set up yet" message (`SETUP_MESSAGES` in `apps/web/server/env.ts`). Don't re-add code that hides them when `features.*` is off.
- **Any GGUF model from Hugging Face (desktop)**: `src/models/huggingface.ts` searches Hugging Face's API (which also reports each repository's architecture), `src/models/architectures.ts` lists what the pinned llama.cpp loads (regenerate with `node scripts/engine-architectures.mjs` whenever `engine.lock.json` changes; a test compares the releases), and `src/models/hfStore.ts` keeps added models in localStorage, checked on every read (ids `hf-…`, Hugging Face https addresses only, `model.gguf`/`mmproj.gguf` only). They download, load and remove like catalog models; the main process still accepts only huggingface.co addresses and exact sizes. Split (multi-part) GGUFs and files under 3 bits are not offered. `quo://models/huggingface/<owner>/<name>` links (Hugging Face's "Use this model", `src/links.js`) only open that model in Models & storage; keep it that way: a link never downloads, runs or takes a path.
- **One `InferenceEngine` interface, two engines** (`apps/web/src/engine/`): wllama in the browser, and `nativeEngine.ts` in the desktop app (chosen at load time by `window.quoDesktop.engine`). The desktop catalog (`DESKTOP_MODELS` in `catalog.ts`) is separate from the browser's; model files there are always stored as `model.gguf` (+ `mmproj.gguf`).
- **Desktop engine builds are official llama.cpp releases**, not the npm bindings (`@fugood/llama.node`, `node-llama-cpp`): the bindings ship generic x86 builds that ran ~3x slower on CPU. Voice stays in the renderer (Transformers.js) because the native whisper bindings ran at 0.2x real time on CPU. Update llama.cpp only through `engine.lock.json` and `npm run check:engine` (apps/desktop/README.md). macOS universal builds need `mac.x64ArchFiles` for the engine folders. Linux ships x64 (Vulkan) and arm64 (processor) builds; Windows ARM waits for an update channel of its own (electron-updater gives Windows no arm64 choice). **The optional CUDA engine (`src/engine/accelerators.js`) is the only code the app downloads**: only when the person asks, only the files named in the lock's `accelerators` (same release), only from llama.cpp's GitHub release and GitHub's own redirect hosts, each archive checked against its SHA-256 before unpacking, installed only after it lists a CUDA device, and set aside (back to the bundled engine) when it fails to start. The page can only ask; it never supplies a name, address or path. `test/accelerators.test.js` tries to abuse each step; a change there needs a test too.
- **Code colours and maths load on demand from the app, never a CDN** (`src/code/`: Shiki with the JavaScript engine and a curated `LANGUAGES` list; `src/math/`: KaTeX via remark-math). Colours are roles (`code/theme.ts` names them; their values per appearance are in `styles/appearances.ts`, AA on `--code-bg`, tested); never put a hex colour in the theme. Their chunks are named `lang-*`/`math-*` (`chunkName` in vite.config.ts) so the service worker caches them on first use instead of on install; a new lazy chunk needs the same. Maths text goes through `normalizeMath` (`\( \)`, `\[ \]`, money as text, never inside code) and KaTeX runs with `trust: false`.
- **The WebAssembly runtimes are hosted by the app, never a CDN.** Speech: `voice/whisper.worker.ts` sets `wasmPaths` (Transformers.js defaults to jsDelivr, which would break the privacy promise); `dropUnusedSpeechRuntimes` in vite.config.ts removes the 27 MB variants nothing loads. Models: wllama fetches its compatibility build (Safari, older Chrome) from jsDelivr unless told otherwise, so `localEngine.ts` always calls `setCompat` with the app's copy (`engine/compat.ts`, loaded only where needed, left out of the desktop app). A browser model with a file of 2 GiB or more is offered only where wllama's main build runs (`engine/wasm.ts`); the compatibility build can't load it.
- **Quo Sync's crypto format is a public contract** (`src/sync/crypto.ts` on the web, `services/sync/crypto.ts` on the phone, SYNC.md): changing the key derivation, AAD or blob layout without bumping the version byte strands every user's cloud copy. `src/sync/__tests__/vectors.json` holds records both implementations wrote and must read; the engine is tested end to end against the real server code (`src/sync/__tests__/engine.test.ts`), and the phone against the web in `apps/web/interop/` (`npm run test:interop`). Keep all three passing.
- **The sync engine is shared, not duplicated.** `engine.ts`, `merge.ts`, `kinds.ts`, `wire.ts` and `recovery.ts` are the same files in `apps/web/src/sync/` and `apps/mobile/services/sync/` (the phone app can't import from outside its folder). Edit the web copy, then `node scripts/check-shared-sync.js --fix`; CI fails if they differ. They must stay free of platform globals (no `crypto`, no DOM, no React Native).
- **Attachments go with the message to every model** (`shared/content.ts`): to an offline model they stay on the device; to a cloud model or one reached with the person's own key (Claude Agent included) documents travel as text and images as data addresses of JPEG/PNG/WebP/GIF only (never a web address), the newest `MAX_REMOTE_IMAGES` per request (`buildContext`'s `maxImages`), and only to models that read images (`vision` in `server/cloudModels.ts`, from OpenRouter's input_modalities). The server and the desktop app (`claude/validate.js`) check every image part; Code mode messages stay text. The privacy page says so: change it with the behaviour.
- **Making images** (`apps/web/src/images/`, `server/images.ts`): the chat's own model writes the image prompt, and Quo's server makes the image through OpenRouter's image API (`IMAGE_MODELS`: FLUX 3 Klein for new images, Gemini 3.1 Flash Lite Image for changes, which takes the last image as its reference and is also the fallback when FLUX queues). Cloud and own-key models (Claude Agent too) are told to write `<image aspect=… edit="last">prompt</image>` (`IMAGES` in `shared/prompts.ts`); the page takes those lines out of what is shown (`showingImages`) and makes them after the reply. Offline models have no such rule (small models): `/image …` has them, and Code mode, write just the prompt in a side call (`IMAGE_WRITER_PROMPT`), so only the prompt leaves the device; in an offline chat, only the message right after an image first goes to a side call (`IMAGE_FOLLOW_UP_PROMPT`, `replyWithImageFollowUp`) that decides whether it asks for a picture or a change ("remove the apple"), so other chats pay nothing extra. On the device a change goes to a downloaded model that changes pictures (FLUX.2 klein) even when another is chosen for new ones. Images are free a few a day (`FREE_DAILY_IMAGES`: new ones on FLUX only, with no fallback; a change counts as two), then credits held for the dearest model and settled at OpenRouter's cost; the server takes only a prompt, a shape and an image to change as image data. Made images stay on the device, never synced; later turns tell the model what it made (`modelText`). The privacy page says so: change it with the behaviour. **On the device (desktop app):** stable-diffusion.cpp (`apps/desktop/src/images/`) makes images from an image model the person downloaded; the page gives only its id, a prompt and a shape, and main builds every argument (no path, option or program from the page). It is bundled beside llama.cpp, never downloaded. The person's own image model files are chosen only in a native dialog, recognised by their tensors (`families.js`), and only their id, name and family ever reach the page.
- Attachments' contents (images, document text) are never synced, only their names (`toWire` in `src/sync/adapters.ts`, `toWireMessage` in `services/sync/convert.ts`). The long-chat summary and other derived data never leave the device.
- Chat ids are the server's record ids unchanged; every other kind is prefixed (`memory:<id>`). An old client that doesn't send `kinds` to `pull` gets chats only. Don't change either without a plan for clients already out there (desktop 1.1 is).
- **Cloud models** are listed in `apps/web/server/cloudModels.ts`; clients fetch them from `/api/models`. Every id must exist on OpenRouter (check against https://openrouter.ai/api/v1/models, which also has current prices and release dates), and prices are what OpenRouter charges. `tier: 'frontier'` models are the flagship ones, shown in the picker behind a lock. A model is locked until the person is signed in and has credits for a typical message (`lockOf` in `src/cloud/access.ts`: one rule, used by the picker and `App.choose`, which opens the paywall instead of switching). Don't hide paid models when accounts aren't set up: they stay visible and the paywall says so. Figures the app shows are copied from the server: plan prices (`src/cloud/prices.ts` ↔ `server/billing.ts`) and the trial (`TRIAL` ↔ `TRIAL_CREDITS` in `server/credits.ts`); change both together.
- **Thinking is per model, not one switch** (`apps/web/shared/thinking.ts`, `thinking` in `server/cloudModels.ts`): OpenRouter describes each model's reasoning (some always think, some can be off, the efforts differ), the catalog records it, the app offers only the levels a model really has (Off, Quick, Auto, Deep), and Auto sends nothing so the model decides for itself. The free model is held to a low effort (its tokens cost Quo). Code mode leaves thinking to the model. When models are added or updated, run `npx tsx scripts/check-reasoning.ts` in apps/web and fix what it reports; never send an effort a model doesn't list.
- **Code mode (the coding agent) is security-critical; read `apps/desktop/README.md` → Code mode before touching it.** The rules that must not erode: the project folder is chosen only in a native dialog, or is a new empty folder the app itself makes under `Documents/Quo Projects` (`workspace.js`: the page supplies only a name, reduced to `[a-z0-9-]`), and the page holds only an id; edits, commands and commits are approved only in windows made by the main process, never anything in the page: Quo's own styled approval window (`apps/desktop/src/approval/`: a separate window with an isolated renderer, a strict content policy, model text drawn only with textContent, answers accepted only from that window, closing means no) or the plain system dialog as the fallback; every model-supplied path goes through `resolveInside` (a path outside the project is read only after a native approval of that folder, and then against that folder as its own root: `external.js`; the changing tools never take one); secrets files are unreadable and well-known token formats redacted; network access is the GitHub zip download, the web tools (see the next bullet) and `git_push` to a remote the project already has, approved each time; the tool list and system prompt are owned by the server or, for the user’s own API keys, the app (`shared/agentTools.ts` for the tools, `shared/prompts.ts` for every prompt). Add a tool in three places that must agree: `shared/agentTools.ts` (schema), `desktop/src/agent/session.js` (`TOOL_NAMES` and dispatch), `web/src/agent/describe.ts` (what the chat says), and give it a test that tries to abuse it. The sandbox model (`openrouter.ts` stand-in) can run the whole loop without an API key. Anything that runs without asking (`commands.js`) must be *recognised*, never filtered: widen that list only with a test that tries to abuse the new entry (writes, reads outside the project, secrets, chaining, Windows). Settings that can run commands (`isProtectedPath`) stay read-only to the agent. **Approval levels** (`apps/desktop/src/agent/autonomy.js`): sessions start at "ask"; "risky" and "all" (which also skips commit approval) are set only by main after a native dialog, per session; pushes always ask, and no level loosens the fixed limits above. Widening what "risky" lets through needs a test that tries to abuse it.
- **Commits made by Quo (`apps/desktop/src/agent/commit.js`) are security-critical and credit Quo as co-author.** The app, not the model, writes the `Co-Authored-By` trailer (its address is the noreply email of `quo-code`, the GitHub user account that stands for Quo; change both together), only when the "Credit Quo in commits" setting is on (default), and every commit goes through its own native approval dialog with no "for this session" option (unless the person chose the "all" approval level for the session). Keep: explicit file list committed with `--only`, `--literal-pathspecs`, secrets/protected paths refused, no git identity set or invented, hooks-path edits refused, `commit.js` never pushes. **Pushing is only `git_push` (`push.js`)**, behind the "Let Quo push and open pull requests" setting (on by default): it takes no arguments from the model (current branch to its upstream, or `origin`/the only remote, already configured), never forces (refuses when behind), asks every time with no "for this session", shows the remote without credentials, and gives a GitHub compare link for a pull request instead of using any token. `gitGuard.js` sends `git commit`/`git push` commands back to those tools and refuses force pushes, amends and `--no-verify`; it guides the model and is not the security boundary (approvals are). Git for these two tools keeps only the SSH/gpg agent sockets on top of the scrubbed environment (`gitcmd.js`). Tests in `test/agent/commit.test.js`, `push.test.js` and `gitGuard.test.js` try to abuse each.
- **Background commands and the `task` helper are bounded versions of tools that already exist.** Background commands (`apps/desktop/src/agent/background.js`) start only after the same native approval as any command, are limited in number, scrubbed like other commands and killed when the Code session ends. The helper (`apps/web/src/agent/subagent.ts`, `role: 'explore'` in `server/chat.ts`) can only ever have the reading tools: the server ignores the tools the app asks for in that role. Keep both limits when changing either, and test the abuse. Long-session summaries (`apps/web/src/agent/summarize.ts`, server role `summarize`) get no tools, are carried as labelled notes inside the person's message, and fall back to dropping old output.
- **Prompts are written the way models are asked to write** (`apps/web/shared/prompts.ts`, every system prompt in one place): plain English in the spirit of ASD-STE100 Simplified Technical English. One rule per line, short imperative sentences, common words, one word for one thing, no rule said twice. The shared "How to write" block (answer first, no filler or stock phrases, no closing offer, same style in what the model makes) goes in every prompt; offline models get its one-line form. Tool details belong in the tool descriptions (`agentTools.ts`), not in the prompt. Keep the safety rules when shortening: prompt tests check each of them.
- **What models are told about the moment** (`apps/web/shared/environment.ts`) stays three short lines: the date on the person's clock (not the time: see the next bullet), which model it is and where it runs, and one line about not guessing. Do not grow it: every line added after a bad answer (what a model "cannot" do, time zone or place, rules for one kind of question) made small models refuse plain questions or talk about the prompt. Never include where the person is (only the clock's offset from UTC is used, and it is not shown). For Quo's cloud models the server builds the note from its own clock and the model list, and checks the one field the app sends. Keep it at the end of the prompt (the fixed part before it stays cacheable).
- **The user's own API keys are security-critical** (`apps/web/src/providers/`, `apps/desktop/src/providers/`; see "Your own API keys" in `apps/desktop/README.md`). Must not erode: the page never reads a key back (`providers:list` returns the last four characters); main decides where a key goes (built-in addresses in `registry.js`, custom servers stored in main, editing an address deletes its key); only the chat call and model list, by exact path; headers come from main; redirects are refused; errors never hold a key; keys are encrypted with `safeStorage` or kept in memory, never in the clear. A new provider goes in both registries (a web test compares them). Browser keys stay in localStorage, never synced. Treat these models like cloud models for privacy: no memories.
- **Claude Agent (`apps/desktop/src/claude/`, desktop only) is security-critical** (see "Claude Agent" in `apps/desktop/README.md`): Claude through the person's own Claude Code login, as OpenCode does it. Must not erode: Quo never reads, stores or relays the login or a token, and never changes or proxies Claude Code's requests; it says who it is (`quo-desktop` as Claude Code's entrypoint label, never another program's such as `cli`) and drops what a Claude Code session that started Quo hands down (`SESSION_MARKERS` in `options.js`); only their own `claude` runs (the SDK's npm package is a dev dependency because it bundles Anthropic's copy; the app ships only `sdk.mjs`); Claude Code starts with no tools, settings, hooks, skills, memory or MCP servers of its own, `dontAsk`, only `mcp__quo__*` allowed; its tool calls are only handed back to the page, which runs them through Code mode's approvals; the page sends only a model name, the conversation, the tools, the Thinking choice and a side-call mark (`validate.js`); the page never learns the account's email; transcripts are deleted once Quo drops a conversation, on quit, and swept after a crash. The name is "Claude Agent" (Anthropic's branding rules forbid "Claude Code" as a product name). It is in releases since 1.7.2 under Anthropic's terms for running Claude Code in another product (code.claude.com/docs/en/legal-and-compliance: the binary unmodified and never shipped, no sign-in method removed or restricted, sign-in only in Anthropic's own flow, no credential handled, usage never paid for, resold or relayed by Quo); `IN_RELEASES` in `claude/release.js` lists them and is the switch that takes it out again. Never add a Claude.ai sign-in of Quo's own, ship or change Claude Code, or handle a token: any of those breaks the terms.
- **Documents in Code mode** (PDF and Office files, `apps/desktop/src/agent/files/documents.js`, `reader/`): their text is never taken out in the main process, which holds the person's keys. In the app it's a hidden sandboxed window with no Node, in its own session that serves only the reader's own files and refuses everything else (outside Electron, a Node process under the permission model); it gets bytes from main, never a path, with a time limit, and zip bombs are refused. **Quo's own local pages** (approval window, document reader) load over `app://` from a fixed file list (`serveLocalPage`), never `file://`: the fuses make `file://` fail from the asar. Run `npm run smoke` on a packaged build after touching either.
- **Tool servers (MCP, `apps/desktop/src/mcp/`) are security-critical**: they are added only in the person's own `mcp.json` (the page can't write it and never sees a command, argument or env value); one runs only after a native dialog showed exactly what it runs, and a changed entry is off until approved again (fingerprints in `mcp-approved.json`); servers get the scrubbed environment and may ask Quo nothing but `ping`; every tool call goes through the approval window (`mcp/approve.js`), plan mode refuses them and "risky" still asks; results are text, redacted and clipped. Their tools go to models only through `toolServerTools` (`shared/agentTools.ts`), beside Quo's own and never for helpers, summaries or the free model. Widening any of this needs a test in `apps/desktop/test/mcp/` that tries to abuse it.
- **The local server for other apps (`apps/desktop/src/server/localApi.js`) is security-critical**: off by default and turned on only after a native dialog; 127.0.0.1 only, Host must be that address, any Origin header refused, Quo's own key required, only the three OpenAI routes, llama-server's key never leaves main. Widening it needs a test that tries to abuse the new part.
- **Web search (`apps/desktop/src/web/`) is security-critical** (see "Web search" in `apps/desktop/README.md`). Must not erode: the model may open only an address the user wrote, a search returned, or a page it read links to, exactly as written (`sessions.js`); only public addresses, checked at connect time and on redirects (`guard.js`); no cookies, GET only, limits; queries are cleaned of secret formats; search keys are stored and never read back like provider keys. Offline-model chats start with Web off on purpose (offline stays offline; web tools cost photos, documents, thinking). Never route a Quo-paid search through the free model.
- **Anything added inside `.composer-wrap` must set `pointer-events: auto`**: the area ignores clicks except on its own parts (it floats over the messages), and a banner without it looks fine and does nothing. **Colours are roles, never values.** `styles/appearances.ts` holds every role (`--ground`, `--sheet`, `--ink`/`--ink-2`/`--ink-3`, `--rule`/`--rule-strong`, `--indigo`/`--indigo-fill`/`--on-indigo`/`--indigo-wash`, `--sky` for the cloud, `--danger`/`--caution`/`--add`, `--syn-*`) in each appearance: Light, Dark, Black, High contrast, High contrast dark, E-ink. `npm run tokens` writes `styles/tokens.css` from it; `appearances.test.ts` fails on a missed contrast pair, a stale tokens.css, a colour written in any other stylesheet, or a desktop window colour (`GROUNDS` in `apps/desktop/src/theme.js`) that doesn't match. Which appearance applies is `theme.ts`: a mode (system, light, dark) and three switches, each automatic until changed (Black: on for phones, off for computers and always off in the desktop app unless chosen; High contrast: the system's setting; E-ink: e-ink screens). It sets `data-env` on `<html>` and gives the desktop app the mode (Electron's `nativeTheme`, which the approval window follows; `approval.css` copies Light's and Dark's colours, since that window can't load the page's styles). One solid indigo per screen (Send, Download): actions repeated in lists, banners and nudges are line buttons (`btn-glass`); selection is `--indigo-wash`, hover is `--sheet-2`. Text sizes are the `--t-*` tokens (rem, so they follow the person's text size) and radii the four `--r-*` levels; facts about a thing are separate items (`ui/Facts.tsx`), never joined with dots. Surfaces are solid (`.glass` is the old name of the sheet surface): no gradients, blur or glow. Type is Atkinson Hyperlegible Next and Mono, bundled in `styles/fonts/`, never a font service. Motion shows state only: parts of the interface arrive with `rise` (`styles/motion.css`); what the model makes (words as they're written, thinking, Code mode steps, pictures) and its work in progress dissolve and sweep through the 2px Bayer dither (`styles/dither.css`, newest words timed in `ui/fresh.ts`), in indigo on the device and sky in the cloud (`--made`, from `data-where`). Menus and sheets never dither; scanlines and glow stay out. All of it stops for reduced motion and in E-ink. Where a reply ran is always shown (`ui/chat/Where.tsx`): under each reply, in the composer, in the chat list, and as a note where a chat moves to the cloud or to the person's own key and back.
- **Keep the start of every prompt the same from turn to turn.** llama.cpp (desktop, and wllama in the browser), llama.rn and the cloud providers reuse the cached start of a prompt; anything that changes early in it makes the whole conversation be read again (measured in the browser: 2 s with the cache, 114 s without, for a 2,300-token chat). So the system prompt holds nothing that changes per turn (the date, not the time, in web and phone alike), old chat messages are dropped in steps of `TRIM_STEP` (`src/chat/context.ts`), and Code mode leaves old tool output out in groups of `TRIM_RESULTS_STEP` (`src/agent/loop.ts`); tests check each. Never edit earlier messages per request.
- **Connection awareness** (`apps/web/src/net/`): switching only ever goes *toward* the offline model, never to a cloud one; coming back online only offers to return.
- **Code mode on offline models** (`apps/web/src/agent/local.ts`, `capability.ts`, `support.ts`): sessions are *compact* (`COMPACT_LIMITS` in `desktop/src/agent/session.js`) and the engine loads with `AGENT_CONTEXT`; keep tool results small, a small window is the main failure. Ratings (`agent` in the catalog) are judgment and only decide whether to ask first; they never loosen approvals. Don't pass the catalog's sampling to tool calls: the repetition penalties break code and JSON.
- **Memories (web and desktop)** live in the `memories` store of the same IndexedDB database as chats, opened only in `src/db.ts`: add a store by raising the version and adding an `oldVersion <` branch, never by recreating (`src/memory/__tests__/store.test.ts` upgrades a real v1 database). They go into the prompt of *offline* models only (`memoryPrompt`, in `ui/Chat.tsx`); never add them to a cloud model's prompt: that would send personal facts to a third party, against what the app promises.
- **Who is signed in is decided by the database, not just the token** (`identify(db, request)` in `server/identity.ts`, async): the token must be genuine and unexpired, the account must exist, and the session must be newer than `users.sessions_valid_after` (set by `POST auth/signout-all`). Never read a user id straight from the token (`readSession`); a signed-out request costs no query. Sync routes also pass through a per-account call limit (`takeSyncCall`).
- **Account deletion exists and must keep working** (`POST account/delete`): Google Play requires in-app deletion for any app that lets people create an account. If you add a table with a `user_id`, add it to `handleAccountDelete`. `trial_claims` (keyed hashes of email addresses, no `user_id`) deliberately stays for a year after deletion so the free trial can't be claimed twice; the privacy and delete-account pages say so.
- `SYNC_API_ORIGIN` (`apps/mobile/constants/sync.ts`) is the hosted API's address; it moves with the domain, alongside `WEB_APP_URL`, `API_ORIGIN` and `LINKS.webapp`.

## Keeping the repository clean

- **Nothing sensitive is committed.** `scripts/check-secrets.js` (CI runs it with `--history`; the pre-commit hook is `scripts/hooks/pre-commit`, turned on once per clone with `git config core.hooksPath scripts/hooks`) blocks secrets files by name, secret formats, home folders with a real name in them and email addresses that aren't ours. It never prints what it found. Tests that need a fake key or address build it at run time (`'gh' + 'p_'…`), because the scanner is strict on its own tests too. The root `.gitignore` covers secrets everywhere.
- **No source file over 500 lines** (`scripts/check-structure.js`, in CI). Older long files (mostly in `apps/mobile`) are listed there at their current length and may only shrink; when one drops under the limit, take it off the list. Split by what the code does, one concern per file: see `apps/desktop/src/agent/files/`, `apps/web/src/ui/chat/` and `apps/web/src/styles/` for the pattern. Tests follow the code (`apps/desktop/test/agent/`), with shared setup in a `helpers.js`.
